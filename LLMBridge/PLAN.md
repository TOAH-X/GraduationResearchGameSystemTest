# LLMBridge 実装計画

Python を橋渡しにして、LLM（OpenAI API）が選んだ「意図」を Unity ML-Agents のゲームに送る仕組みを作る。

- 作成日：2026-11-11（同日更新：モデルの決定、課題への対策を反映）
- 状態：**段階1 完了**（§9）。段階2aは未着手（2026-11-11 に段階を7つに並べ直した。2026-11-12 に「Player を Default にする」方式と時間の単位を決めた。§5.1、§5.5）

---

## 1. 目的

- LLM は毎フレームの操作をしない。数秒ごとに、あらかじめ定義した意図（3〜5個）から1つを選ぶだけ
- 毎判断の細かい操作（移動）は、Python 側の「変換役」が意図にもとづいて決め、被支援プレイヤー（Player）に送る（§5.1。変換の中身は段階4で決める）

```
LLM →（数秒ごと）意図 → 変換役（Python）→（判断ごと＝3フレームごと）横・縦の移動 → Player
```

## 2. 使う場面

| 場面 | LLM | 支援エージェント | ゲームの進み方 |
|---|---|---|---|
| 配線確認（この計画の段階1〜6） | 使う（モックが標準） | 推論のみ | ロックステップ |
| **LLMプレイ時** | LLM が**被支援プレイヤー**を操作する | 推論のみ（**学習しない**） | ロックステップ |
| 再学習時 | 使わない（報酬は固定済み） | `mlagents-learn` で学習 | 通常の学習 |
| 人間がプレイする本番 | 使わない | 推論のみ | リアルタイム |

→ LLM を使う場面はすべてロックステップでよい。**非同期方式は不要**。

## 4. ルール

**APIキー**
- コードに書かない。環境変数か `LLMBridge/.env` から読む（`.env` は `.gitignore` に入れる）
- ログ、標準出力、エラーメッセージ、コミット、チャットに出さない。`sk-` で始まる文字列は `sk-***` に置き換えてから出力する
- 値を空にした `.env.example` を用意する
- **`.env` を作るより先に `.gitignore` に追記する**（`.env` が誤ってコミットされないようにするため）

**APIの使い方**（大切に使う）
- モックを標準にする。実APIは `--real` を付けたときだけ呼ぶ
- `--max-calls` で1回の実行あたりの呼び出し回数に上限を設ける。リトライも1回として数え、上限に達したら**終了**する

**Python**
- Python 3.8 で動く書き方にする（`typing.List` / `Optional` を使い、`list[str]` や `X | Y` は使わない）
- 既存 venv のパッケージのバージョンは変えない。新しくインストールするものもない（`.env` の読み込みは自作する）
- Windows での文字化け対策：起動時に標準出力を UTF-8 に切り替え、ファイルの読み書きはすべて `encoding="utf-8"` を明示する（何も指定しないと cp932 になるため）

**記録と変更**
- 使ったモデル名、プロンプト、応答はファイルに保存する（キーは保存しない）
- 既存の Unity プロジェクトの変更は最小限にし、一覧（§7）で管理して元に戻せるようにする
- 削除や上書きなどの破壊的な操作は、事前にユーザーに確認する
- 不明な点は推測で進めず、質問する
- 各段階で動作を確認できてから次へ進む。実装はユーザーの明示的な指示があってから始める

## 5. 技術的な判断

### 5.1 Player を Default にして Python から操作する（2026-11-12 決定）
Unity が Python と足並みをそろえて止まるのは、`BehaviorType = Default` のエージェントが判断を求めたときだけ（`RpcCommunicator.DecideBatch` / `PutObservations` で確認）。B_Scene で有効なエージェントは Player（Heuristic＝キーボード）と SubPlayer_Another（Inference）だけなので、そのままでは同期しない。

当初は「同期用のダミーエージェントを足す」案だったが、LLMプレイ時は人間が操作しないので、**新しいシーンの Player を `Default` にする**ことにした。

| | A. Player を Default（採用） | B. ダミーを足す（見送り） |
|---|---|---|
| 変換役の置き場所 | Python | Unity（C#） |
| 状況 | Player の観察142個（自分の位置、近い敵20体、近い弾15発）が判断ごとに自動で Python に届く | 別の経路が必要 |
| Player の動かし方 | ML-Agents の通常の仕組みのまま | 今の Player はキーボードを読む作りなので、既存スクリプトを変えずに動かすには部品の差し替えが必要（複雑） |

- 判断は3フレームごと（`DecisionPeriod=3`。B_Scene で人間が遊ぶときも同じ）。Python が操作を送れるのは判断のときだけ
- Player の操作は連続値3つ（横・縦・ショット）。ただし既存コードでショットは常に出る設定なので、実質は移動だけ（`PlayerAgent.cs` 558行目）
- `Default` では Player の開始位置の横位置がランダムになる（学習用の工夫。§8）
- Python なしで再生すると、Player は設定済みの Player.onnx で動く
- 変換役のルールは Python で書くので、コメントで丁寧に説明する

### 5.2 意図の扱い
意図は **Python の中だけで完結する**（LLM が選び、変換役が操作に変える）。Unity は意図を知らなくても動く。
画面に意図を表示したい、Unity 側で記録したい、などの必要が出たら、`EnvironmentParametersChannel`（キー `intent`）か段階3のサイドチャンネルで送る。

### 5.3 状況の送り方（段階3で実装）

Player の観察142個は自動で届く（§5.1）。それ以外の情報（被弾、HP、相方との距離、判断していないフレームの情報など）を足す方法の比較：

| | 観察を増やす | 自作サイドチャンネル（JSON） |
|---|---|---|
| 実装量 | 少ない | Unity側・Python側に1クラスずつ |
| 判断との同期 | 厳密 | 判断ごとに届く（全フレーム分をまとめて送れる） |
| 項目の追加 | 固定長の float。観察数の設定も変える必要がある | キーを足すだけ |
| 数が変わるデータ（敵や弾の数） | 上限の数だけ枠を取り、空きを埋める必要がある | リストのまま送れる |
| LLMプロンプトへの変換 | 添字の対応表が必要 | ほぼそのまま使える |

**推奨：自作サイドチャンネル（仮称 `GameStateChannel`）**。観察を増やすと既存の `PlayerAgent.cs` を変えることになり、学習済みモデルとも合わなくなる。LLM に渡すのは意味のついた可変長の情報でもある。

- **全フレームの情報を送る**（2026-11-12 合意）：Unity 側で判断と判断のあいだの3フレーム分をまとめ、判断のときに一緒に送る。やり取りの回数は増えず、同じPC内の通信なので追加の時間はミリ秒未満の見込み（段階3で実測する）。1ゲーム（3000フレーム）でも記録は数MB程度
- Python は全部をログに保存し（分析用）、LLM には要約だけを渡す（数秒ごと）
- 重くなりうるのは通信より、Unity 側で毎フレーム情報を集める処理。集める項目と方法は段階3で決める
- 接続時に Unity の設定値（`FIXED_DT`、`DECISION_PERIOD`）も送り、Python の `settings.py` と照合する（§5.5）

### 5.5 時間の単位（2026-11-12 決定）

| 呼び方 | 中身 | 今の長さ | 使い方 |
|---|---|---|---|
| **フレーム** | FixedUpdate 1回。ML-Agents の1歩と一致する | 0.02秒 | **内部の基準**。記録の主な時間軸 |
| 判断 | Player が行動を決める1回 | 3フレーム（0.06秒） | Python が操作を送れるタイミング。記録にも残す |
| ゲーム内秒 | フレーム数 × `FIXED_DT` | — | 人が読むための表示 |
| 描画フレーム | 画面の更新1回 | PCの性能で変わる | 使わない |

- 人が指定する値（長さ、LLM を呼ぶ間隔など）は**フレームでも秒でも指定できる**。標準はフレーム（例：`--llm-interval-frames 150` または `--llm-interval-sec 3`）
- 判断の間隔で割り切れない値は、直後の判断に合わせて、そのことを表示する（例：100 → 102）
- 記録には、判断ごとにフレーム番号・判断番号・ゲーム内秒を残す（後で時間軸を変えられるように）
- `FIXED_DT=0.02` と `DECISION_PERIOD=3` は変わる可能性があるので、コードに直接書かず `settings.py` の1か所にまとめる。段階3以降は、接続時に Unity から実際の値を受け取り、食い違えば警告する

### 5.4 モデルの選定（2026-11-11 決定）

**`gpt-6-luna`（reasoning effort = `none`）** にする。

| | `gpt-6-luna`（採用） | `gpt-4o-mini` | `gpt-5-nano` | `gpt-6-astra` |
|---|---|---|---|---|
| 料金（100万トークンあたり、入力/出力） | $0.10 / $0.50 | $0.15 / $0.60 | $0.05 / $0.40 | 高い（最上位モデル） |
| 状態 | 現行 | 非推奨。2027-01-14 に廃止予定（後継が `gpt-6-luna`） | 非推奨 | 現行 |
| 見送った理由 | — | 高く、まもなく廃止 | 非推奨 | 用途に対して高すぎる |

- 選んだ理由：最新世代でいちばん安い。公式が「速さと費用を重視するならこれ」と案内している。Chat Completions と Structured Outputs に対応している
- `none` にする理由：推論の強さは `none / low / medium（標準）/ high / xhigh / max` から選べる。`none` なら思考を飛ばすので速く、思考に使うトークンの料金がかからない。さらに「出力の上限を思考で使い切って、応答が空になる」問題も起きない
- 費用の目安：疎通確認1回で 0.001円未満、意図の選択1回で 0.01円程度、LLMプレイ1ゲーム（約20回）で 0.3円程度
- **確認済み（2026-11-11）**：公式ページは Responses API の書き方（`reasoning.effort`）でしか説明していなかったが、段階1の実API呼び出しで、Chat Completions では `reasoning_effort` と `max_completion_tokens` がそのまま通ることを確かめた
- 出典：[GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna.md)、[Pricing](https://developers.openai.com/api/docs/pricing)、[Deprecations](https://developers.openai.com/api/docs/deprecations)、[GPT-4o mini](https://developers.openai.com/api/docs/models/gpt-4o-mini)、[GPT-5 nano](https://developers.openai.com/api/docs/models/gpt-5-nano)

## 6. 段階ごとの計画

### 全体（2026-11-11 に並べ直した）

| # | 段階 | やること | 前提 | 不確実さ | API |
|---|---|---|---|---|---|
| 1 | APIの疎通 | ✅ 完了 | — | — | 使用済み |
| 2a | Unity との配線：接続と同期 | 新しいシーン（Player を Default）、Python から Player を操作して止める・進めるだけのループ | なし | **高い** | 使わない |
| 2b | Unity との配線：意図と耐久 | ランダムな意図で仮の操作を切り替える。65秒の待機、シーンの再読み込み、エピソードの区切りに耐える | 2a | **高い** | 使わない |
| 3 | 状況の送信 | 自作サイドチャンネル（C#）で、全フレームの状況と Unity の設定値を Python に送る | 2 | 中 | 使わない |
| 4 | 意図の実行 | Python の変換役が、意図を Player の操作に変える。意図どおりにいったかを状況から判定する | 2、3 | **高い**（研究上の設計判断） | 使わない |
| 5 | 意図の選択 | 状況のJSONから LLM に意図を選ばせて検証する。モック→実API | 1、3 | 低い | 少し使う |
| 6 | 統合 | 2〜5をつなぎ、LLM が選んだ意図でゲームが動くことを確かめる | 2〜5 | 中 | 使う（回数を絞る） |
| 7 | 運用 | LLMプレイでデータを集める（ログ、ゲーム数、費用、所要時間） | 6 | 低い | 本格的に使う |

```
1 ──────────────────────────────────────┐
2a ─ 2b ─ 3（状況の送信）─┬─ 4（意図の実行）─┤
                          └─ 5（意図の選択）─┴─ 6（統合）─ 7（運用）
```

**この順番にした理由**
- 当初は、いただいた原案の順番（API → 意図の選択 → Unity）をそのまま使っていた。しかし、Unity との配線は「意図はランダムでよい」としたので、意図の選択には依存していない。そこで、依存関係と不確実さで並べ直した
- **2を最初に**：まだ分かっていないことが一番多く（ML-Agents の同期、長時間の停止、シーンの再読み込み）、ほかのすべての段階の土台になるため。さらに a/b の2回に分け、「つながる・同期する」を先に確かめる
- **3（状況の送信）を4より先に**（2026-11-11 に入れ替えた）：意図の実行では「意図どおりにいったか」を判定して疑似プレイヤーの気分とみなす構想で、その判定にも分析にもゲームの状況が必要になるため（§8）。LLM に渡す状況の形式もここで決まるので、5のプロンプトの作り直しも減る
- **4（意図の実行）を早めに**：意図を受け取っても動きが変わらなければ、LLM に選ばせる意味がない。実行方法は研究の中身に関わる判断で、再学習が必要になると時間がかかるため、3の直後に置く
- **5は後ろへ**：Python だけで完結し、つまずく要素が少ない

### 段階1：APIの疎通

**目的**：API を最小構成で1回呼んで応答を表示する。あわせて、以降の段階でも使う土台（設定の読み込み、エラーの分類、リトライ、回数上限、ログ）を作る。

**作るファイル**
```
LLMBridge/
├─ .env.example        OPENAI_API_KEY= / OPENAI_MODEL=gpt-6-luna / OPENAI_BASE_URL=（省略可）
├─ envutil.py          .env の読み込み
├─ llm/
│  ├─ base.py          LLMClient インターフェース、応答クラス、エラー分類
│  ├─ budget.py        CallBudget（--max-calls の管理）
│  ├─ transport.py     HTTPを送る部分（本物：requests／偽物：FakeTransport）
│  ├─ openai_client.py 実API版（送信は transport に任せる）
│  └─ mock_client.py   APIの代わりに応答を返す（段階5以降で使う）
├─ logging_util.py     JSONL形式のログ出力とキーのマスク
├─ step1_ping.py
└─ logs/               gitignore 対象
```

**作業の順番**：最初に `.gitignore` へ `LLMBridge/.env` と `LLMBridge/logs/` を追記してから、ほかのファイルを作る。

**仕様**
- 設定の読み込み：`KEY=VALUE` 形式。空行と `#` で始まる行は無視する。OSの環境変数があればそちらを優先する。値が未設定なら変数名だけを表示する
- 接続先：`OPENAI_BASE_URL` を省略すれば標準のURL（`https://api.openai.com/v1`）を使う
- リクエストの中身：`model`（`.env` の値）、`messages`、推論の強さ `none`、出力上限。パラメータ名は実API呼び出しの1回目で確定させる（§5.4）
- 応答が空で、`finish_reason=length`（上限で打ち切られた）の場合は、そう分かるメッセージを出す
- 疑似エラーの注入：`--simulate` を付けると、`OpenAIClient` の送信部分だけを `FakeTransport` に差し替える。`FakeTransport` は「1回目は429、2回目は200」のように決められた応答を順に返し、通信はしない。これにより、**本番と同じリトライ・分類・上限のコードを、実APIを使わずに確かめられる**
- 呼び出し方：`complete(messages, max_tokens, json_mode=False)` で、応答文・モデル名・トークン数・所要時間が返る
- エラーの分類とリトライ（最大3回。タイムアウトは接続10秒、応答待ち60秒）

| 状況 | 再試行 | 動作 |
|---|---|---|
| 429 レート制限 | する | `Retry-After` があればその秒数、なければ 2→4→8秒（最大30秒）待つ |
| 429 `insufficient_quota`（残高不足） | **しない** | すぐに停止する |
| 5xx、接続失敗、タイムアウト | する | 上と同じ間隔で待つ |
| 400 / 401 / 403 / 404 | しない | 内容を表示して停止する |

- 回数上限：HTTPリクエストを**送る前**に1回分を消費する。既定値が1なので、既定のままではリトライは起きない
- ログ（`logs/llm_YYYYMMDD.jsonl`、1回の呼び出しにつき1行）：時刻、段階、モデル名、送ったメッセージ、設定値、応答文、トークン数、所要時間、HTTPステータス、エラーの種類、何回目の試行か
- キーのマスク：`sk-` で始まる文字列（`sk-proj-...` も含む）を `sk-***` に置き換えてから表示・保存する。OpenAI の401エラーはメッセージにキーの一部を含むため。リクエストヘッダーは表示もログ保存もしない

**実行方法**
```
cd LLMBridge
..\..\helloworld\env\Scripts\python.exe step1_ping.py                                      # モック
..\..\helloworld\env\Scripts\python.exe step1_ping.py --real                               # 実API（1回）
..\..\helloworld\env\Scripts\python.exe step1_ping.py --simulate rate_limit --max-calls 3   # 疑似エラーでリトライを確認
```
オプション：`--real` / `--max-calls`（既定1）/ `--prompt` / `--max-tokens`（既定16。推論を `none` にするので小さくてよい）/ `--timeout` / `--simulate {rate_limit, quota, timeout, server_error}`

Git Bash で実行する場合は、パスを `../../helloworld/env/Scripts/python.exe` と書く（README にも併記する）。

**期待する出力（成功時）**
```
[step1] mode=real model=gpt-6-luna max_calls=1
[step1] response: pong
[step1] latency=0.84s tokens(in/out)=12/2 calls_used=1/1
[step1] log saved: logs/llm_YYYYMMDD.jsonl
```
失敗したときは、エラーの種類と次に何をすればよいかを1〜2行で表示し、0以外の終了コードで終わる。

**動作確認の手順**（実APIを使うのは最後の1回だけ）
1. `.env` が無い状態で実行し、キー未設定のメッセージが出ることを確認する
2. モックで正常に動くことを確認する
3. `--simulate` で、レート制限は待って再試行し、残高不足はすぐ止まり、上限に達したら終了することを確認する（本番と同じ `OpenAIClient` を通す）
4. `--real` で1回だけ呼ぶ。推論の強さと出力上限のパラメータ名がそのまま通るかも、ここで確かめる
5. `logs/` と画面出力に `sk-` が含まれていないこと、`git status` に `.env` が表示されないことを確かめる

### 段階2a：Unity との配線（接続と同期）

**目的**：Python から Unity Editor に接続して Player を操作できること、Python が止まっているあいだはゲームも止まること（ロックステップ）を確かめる。OpenAI の API は使わない。意図もまだ扱わない。

**すり合わせた前提（2026-11-11〜12）**
- **Player（被支援プレイヤー）を `Default` にして、Python から直接操作する**（§5.1。同期用のダミーは使わない）
- 時間は**フレーム（FixedUpdate 1回）**で数える。人が指定するときはフレームでも秒でも指定でき、標準はフレーム（§5.5）
- 実時間は基準にしない。Python が待っているあいだは、ゲーム画面だけでなく **Editor 全体が固まる**（ML-Agents の通信の中で待つため）
- LLM を使っているあいだ、人間は操作しない
- **過去のものには手を加えない**。B_Scene を複製した新しいシーンだけを変更し、既存のシーン・プレハブ・スクリプトは編集しない
- 2a では C# のスクリプトを作らない。C# は段階3でまとめて作る（作ってよいことはユーザーに確認済み）

**作るもの（Unity）**：`Assets/Scenes/LLM/LLMTestScene.unity`
B_Scene の複製（`.unity` をコピーし、`.meta` は新しい GUID で作る）。複製のほうだけ次を変える。

| 変更 | 値 | 理由 |
|---|---|---|
| Player の Behavior Type | Heuristic（キーボード）→ **Default** | Python から操作するため |
| CSV 出力 5つ | `enableLogging: 0`（`LearningLogCSV`×4、`ActionLogCSV`×1。オープンキャンパス版と同じやり方） | 実験データを汚さないため |
| `GameManager.isReload` | true | 60秒後に会話シーンへ移らず、同じシーンをやり直すため（主に 2b のため） |

- それ以外（`stageID=3`、`simulationSpeed=1`、SubPlayer_Another の設定など）は B_Scene のまま。Build Settings には追加しない
- `Default` の動き方：Python とつながっていれば Python が操作する。つながっていなければ、設定済みの Player.onnx（学習済みモデル）が操作する。つまり **Python なしで再生すると Player は勝手に動く**（キーボードでは動かない）
- `Default` にすると、既存の「学習用の工夫」により **Player の開始位置の横位置がランダムになる**（`PlayerMoveController.cs` 103〜115行目）。2a ではそのままにする（§8）

**作るもの（Python）**
- `settings.py`：時間に関わる値を1か所にまとめる。`FIXED_DT = 0.02`（FixedUpdate 1回の秒数）、`DECISION_PERIOD = 3`（判断の間隔のフレーム数）と、秒⇔フレームの換算関数。Unity 側の設定を変えたら、ここだけを直す（段階3以降は Unity から実際の値を受け取って照合する。§5.5）
- `step2a_connect.py`：

| 項目 | 仕様 |
|---|---|
| 接続 | 「Unity の再生ボタンを押してください」と表示し、最大120秒待つ（ポート5004） |
| 表示 | behavior 名（`Player?team=0`）、観察の数（142）、操作の数（連続値3つ）を表示する |
| 長さ | `--frames 600`（標準。600フレーム＝200判断＝ゲーム内12秒）または `--sec 12` |
| 操作 | 毎判断「その場に止まる」（横0、縦0、ショット-1）を送る。ショットは既存コードで常に出る設定になっている |
| 同期の確認 | `--pause-at-frames 300`（または `--pause-at-sec 6`）で `--pause-sec 5` 秒止まる。止まる前と後の観察（敵や弾の位置）の変化量を、ふだんの1判断あたりの変化量と比べる。同じくらいなら「ロックステップ OK」（止まっているあいだにゲームが進んでいたら、敵が大きく動いているはず）。目視でも、5秒間 Editor が固まることを確かめる |
| 終了 | 接続を閉じる。そのあと Player は Player.onnx で動き出すことがあるので、ユーザーが再生を止める |
| 記録 | `logs/unity_YYYYMMDD.jsonl` に、接続、behavior の情報、判断ごとの記録（フレーム番号、判断番号、ゲーム内秒、実時間、自分の位置）、同期の判定結果を残す |

- フレームで指定した値が判断の間隔（3）で割り切れないときは、直後の判断に合わせて表示する（例：100 → 102）
- エラー時の終了コードは段階1と同じ考え方にする（0=成功／2=設定エラー／5=Unity との接続・通信エラー）

**期待する出力（例）**
```
[step2a] Unity の再生ボタンを押してください（ポート5004、最大120秒待ちます）
[step2a] 接続しました。behavior: Player?team=0 観察=142 操作=連続3
[step2a] 長さ=600フレーム（12.00秒、200判断） FIXED_DT=0.02 DECISION_PERIOD=3
[step2a] frame=300（6.00秒）で 5.0秒停止します…
[step2a] 停止をはさんだ変化量=0.012（ふだんの1判断=0.010前後）→ ロックステップ OK
[step2a] 600フレーム完了。平均 1.2ms/判断
[step2a] 終了しました。log saved: logs\unity_20261112.jsonl
```

**実行の手順（分担）**
1. 私：シーンの複製と値の変更、`settings.py` と `step2a_connect.py` の作成（ファイル操作のみ。Editor は操作しない）
2. ユーザー：Editor で `LLMTestScene` を開き、エラーが無いこと、Player の Behavior Type が Default になっていることを見る
3. ユーザー：Python なしで再生し、Player が学習済みモデルで勝手に動くこと、SubPlayer_Another もいつもどおり動くことを確かめる
4. 私：`step2a_connect.py` をバックグラウンドで起動する（接続待ちになる）
5. ユーザー：再生ボタンを押す
6. 私：結果を確認して報告する。最後にユーザーが再生を止め、コンソールにエラーが無いかを見る

**確かめること（2a の完了条件）**
- 新しいシーンが開け、エラーが無い
- Python なしの再生で、Player が学習済みモデルで動き、ゲームが最後まで進む
- Python から接続でき、`Player` の behavior が見える
- Python が止まっているあいだ、ゲームが進まない（数値と目視で判定）
- 正しく終了でき、Editor 側にエラーが出ない

**気をつけること**
- Player は `MaxStep=1000` なので、1000フレーム（20秒）ごとにエピソードが区切られる。2a は600フレームで終わるので影響しない。2b で扱う
- 既存の `PlayerAgent` は `DontDestroyOnLoad` を使っているので、シーンの再読み込みで重複する可能性がある。2b で確かめる
- ポート5004を `mlagents-learn` などが使っていると接続できない（エラーメッセージで分かる）
- 新しいファイルを置くと Editor がアセットを読み込み直すので、作業の前に Editor で開いているシーンを保存しておく

### 段階2b：Unity との配線（意図と耐久）

**目的**：意図を切り替えながら1ゲーム以上回し、長い待ちとシーンの再読み込みに耐えることを確かめる。意図は Python の中だけで扱い、Unity には送らない（§5.2）。

- 一定の間隔（`--intent-interval-frames 150` または `--intent-interval-sec 3`）でランダムな意図を選び、意図ごとに決めた仮の操作（例：左へ動く、右へ動く、止まる）を Player に送る。画面で Player の動きが切り替わることを確かめる
- 意図の切り替えをログに残す（フレーム番号、判断番号、ゲーム内秒、意図）。後で「気分」の分析に使う時間軸の形をここで固める
- 途中で65秒待ってから再開しても、ループが続くことを確かめる（Python 側の `timeout_wait` は待機時間より長くする）
- 60秒のゲーム終了でシーンが再読み込みされたあとも、Player の操作が続くことを確かめる（`DontDestroyOnLoad` による重複が起きないか）
- `MaxStep` による20秒ごとのエピソードの区切りを、Python 側で正しく扱えることを確かめる
- 作る予定のファイル：`intent/intents.py`（仮の意図）、`intent/controller.py`（意図を選ぶ差し込み口。今回はランダム版）、`unity/env_wrapper.py`、`step2b_unity_loop.py`

### 段階4：意図の実行（概要）
